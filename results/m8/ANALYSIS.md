# M8 analysis: the latency distribution, and what causes the tail

Numbers are from `latency.md` in this folder (fenced clock) and `../m8-plain/latency.md` (unfenced clock). Both were generated by `latency_bench`, 3 runs each, back to back in one session on 2026-09-27. This file is the interpretation.

Reproduce with:
```sh
./build/latency_bench.exe data/12302019.NASDAQ_ITCH50.itch50.sample 3 results/m8 fenced
./build/latency_bench.exe data/12302019.NASDAQ_ITCH50.itch50.sample 3 results/m8-plain plain
```

## Headline

Per book message (A F E C X D U): decode + order store + book update. 3 runs merged, 9.6M samples per clock. Values in ns, reported as histogram bucket upper bounds (at most 6.25% high).

| clock | | p50 | p90 | p99 | p99.9 | p99.99 | max | mean |
|---|---|---|---|---|---|---|---|---|
| fenced | measured | 84 | 152 | 352 | 641 | 2,693 | 28–228 µs, varies by run | 97.0 |
| fenced | **timer (40 ns) subtracted** | **44** | **112** | **312** | **601** | **2,653** | not claimed | 56.9 |
| plain | measured | 62 | 104 | 256 | 577 | 1,410 | 27–488 µs, varies by run | 69.3 |
| plain | **timer (20 ns) subtracted** | **42** | **84** | **236** | **557** | **1,390** | not claimed | 49.3 |

- **Same in every run:** p50 is 84 (fenced) and 62 (plain) raw in all three runs.
- **p99.99 varies by run:** 3,590 / 2,308 / 2,308 fenced, and 1,538 / 1,410 / 1,346 plain.
- **Why the mean misleads:** the mean sits above the p50, pulled up by a few very slow messages.

## Clock choice: fenced vs plain `rdtsc`

| | fenced (`lfence; rdtsc` … `rdtscp; lfence`) | plain `rdtsc` … `rdtsc` |
|---|---|---|
| empty timer pair (median) | 80 ticks = 40.1 ns | 40 ticks = 20.0 ns |
| whole file, **without** the probe | 68.9 / 67.9 / 67.5 ns/msg | 67.2 / 67.0 / 68.3 ns/msg |
| whole file, **with** the probe | 168.8 / 164.2 / 163.4 ns/msg | 118.1 / 116.8 / 116.6 ns/msg |
| **what measuring cost overall** | **+~96 ns/msg (2.4×)** | **+~50 ns/msg (1.7×)** |

- **The overhead only halved, it didn't drop to a quarter.** On this CPU (Ryzen 5 7530U) a single `rdtsc` costs about 20 ns and the counter moves in 20-tick = **10 ns steps**, so ~6–10 ns isn't reachable.
- **After subtracting each clock's own cost, the percentiles agree at the median but not in the tail:**

| minus timer cost | p50 | p90 | p99 | p99.9 | p99.99 |
|---|---|---|---|---|---|
| fenced | 44 | 112 | 312 | 601 | 2,653 |
| plain | 42 | 84 | 236 | 557 | 1,390 |

  In this session the fenced tail is 1.3× higher at p99 and 1.9× higher at p99.99. The fences' cost is not constant: they also disturb the pipeline and the cache, and that shows up in the tail. (In the previous session the two agreed up to p99.9. That difference between sessions is itself a warning about how noisy the tail is on this laptop.)
- **Decision: the fenced clock stays as the reported one.** The rule was to switch if the plain clock gave similar percentiles at a quarter of the overhead, and neither part holds: the overhead halved, and the tails differ.
- **Treat the true tail as lying between the two clocks.** The fenced clock overstates the tail through perturbation. The plain clock may understate or blur individual samples, because the CPU can move the counter reads relative to the timed work.

## Method, and its limits

- **Clock:** the CPU's cycle counter (TSC) at a fixed rate (the CPU reports "invariant TSC": yes) of 1.9962 ticks per ns, calibrated against `steady_clock` over 3 × 200 ms.
  - That rate doesn't follow the core's actual clock. If the core slows down to save power, the same work takes more ticks. That's real latency, and it's meant to show up.
- **Resolution: 10 ns.** Any difference smaller than that can't be seen.
- **Isolated cost, not throughput.** These percentiles are the cost of each message on its own, not its share of pipelined throughput (67–69 ns/msg without the probe). Don't compare the two.
- **What's timed:** one `dispatch()` call (decode + handler). The loop that walks the file is outside the timed span.
- **Nothing excluded:** every message is timed, including the cold start. The first 10% of the file holds 59–154 of each run's 3,197 slowest, against a fair share of ~320, so starting cold doesn't add to the tail.
- **Thread setup:** pinned to one logical CPU (CPU 2) at `THREAD_PRIORITY_HIGHEST`, Windows 11 laptop.
- **Runs:** 3 per clock, each with a fresh handler, with the state hash checked after each run.
- **Build:** g++ 16.2 `-O3 -DNDEBUG`, whole sample file (3.2M book messages).

## Per-type breakdown: which message types own the tail

Raw ns, merged over 3 runs. Subtract 40 (fenced) or 20 (plain) for the work itself.

| type | what it does | n | fenced p50 / p99 / p99.9 / p99.99 | plain p50 / p99 / p99.9 / p99.99 | share of slowest 0.1%, fenced | share, plain |
|---|---|---|---|---|---|---|
| A add | insert into the store; creates a level 43% of the time | 3,908,391 | 84 / 384 / 705 / 5,386 | 62 / 216 / 545 / 2,051 | **50–56%** | **34–41%** |
| D delete | lookup + erase; erases a level 43% of the time | 3,842,760 | 84 / 304 / 577 / 1,603 | 62 / 272 / 577 / 1,090 | 25–30% | **38–41%** |
| U replace | delete + add; changes a level 65% of the time | 512,499 | 136 / 464 / 801 / 7,694 | 104 / 368 / 673 / 3,077 | 11–13% | 10–12% |
| X cancel | partial cancel; never changed a level in this file | 1,273,116 | 72 / 216 / 480 / 1,090 | 62 / 208 / 464 / 897 | 4–5% | 6–7% |
| E executed | lookup; hits the best level | 26,739 | 92 / 609 / 1,090 / 9,746 | 72 / 545 / 929 / 2,821 | 2–3% | 2–3% |
| F add with MPID | as A, but rare | 29,130 | 92 / 545 / 2,308 / 22,570 | 72 / 577 / 1,603 / 30,778 | 1–3% | 1–6% |
| R, S, H … | next to no work (this is the timer floor) | 725,322 | 42 / 42 / 42–62 / 84–136 | 21 / 21 / 21–52 / 52–152 | — | — |

- **Both clocks agree that A, D and U own about 90% of the tail,** and that U has the heaviest per-message tail.
- **They disagree on how the tail splits between A and D:** A dominates with the fenced clock, while A and D are about even with the plain clock.
- **E and F have about 27–29k samples each,** so their p99.99 rests on about 3 messages and isn't meaningful.
- **There were no C messages in this file.**

## `book_changed` vs `book_unchanged`: does changing a price level make a message slow?

Every book message is tagged by whether it inserted or erased a price level (a vector insert or erase). Merged over 3 runs, raw ns:

| clock | messages that… | n | p50 | p90 | p99 | p99.9 | p99.99 | mean |
|---|---|---|---|---|---|---|---|---|
| fenced | **created/erased a level** | 3,732,039 | 92 | 176 | 400 | 737 | **5,899** | 109.9 |
| fenced | changed no level | 5,860,596 | 84 | 144 | 304 | 545 | **1,731** | 88.8 |
| plain | **created/erased a level** | 3,732,039 | 72 | 124 | 336 | 673 | **3,077** | 78.8 |
| plain | changed no level | 5,860,596 | 62 | 92 | 208 | 464 | **929** | 63.3 |

- **At the median, a level change costs only ~8–10 ns more.**
- **In the tail the gap widens:** p99 is 1.3–1.6× higher and **p99.99 is 3.3–3.4× higher**. Both clocks agree on this.
- **Share of the slowest 0.1% that changed a level:** 64–66% (fenced) and 69–71% (plain), against 38.9% of all book messages.

**The same split per message type.** This tells creating a level apart from erasing one:

| type | clock | level changed: p50 / p99 / p99.9 / p99.99 | no level change: p50 / p99 / p99.9 / p99.99 | p99.99 ratio |
|---|---|---|---|---|
| A add (creates) | fenced | 92 / 432 / 833 / 7,694 | 84 / 352 / 577 / 2,308 | **3.3×** |
| A add (creates) | plain | 62 / 304 / 705 / 6,155 | 62 / 136 / 352 / 801 | **7.7×** |
| U replace (erases and/or creates) | fenced | 144 / 480 / 833 / 7,694 | 124 / 432 / 737 / 7,694 | 1.0× |
| U replace (erases and/or creates) | plain | 112 / 384 / 705 / 5,386 | 104 / 336 / 641 / 1,474 | **3.7×** |
| D delete (erases) | fenced | 84 / 336 / 641 / 1,667 | 84 / 272 / 545 / 1,474 | 1.1× |
| D delete (erases) | plain | 72 / 304 / 641 / 1,346 | 62 / 232 / 512 / 961 | 1.4× |

Level-change counts: A 1,697,166 of 3,908,391; D 1,666,785 of 3,842,760; U 331,137 of 512,499. E (9,219 changed) and F (27,732 changed) are in `latency.md` but too small for p99.99. X never changed a level.

**Creating a level is what's expensive; erasing one is nearly free.**
- An add that creates a level has a 3.3–7.7× heavier p99.99 than one that doesn't.
- A delete that erases a level is only 1.1–1.4× heavier.
- Erasing never allocates; creating sometimes does. That points to allocation, and the next section confirms it.
- (The fenced U ratio of 1.0× is an outlier: its "no level change" p99.99 rests on ~18 samples.)

## What makes creating a level slow: allocation

**Test 1: is the same message slow in every run?**

| slowest N | slow in all 3 runs, fenced | slow in all 3 runs, plain | expected by chance |
|---|---|---|---|
| 10 | 0 | 0 | ~0 |
| 100 | 3 | 2 | ~0 |
| 1,000 | 37 | 83 | ~0 |
| 3,197 (0.1%) | 180 | 311 | 0.003 |

- **The extreme outliers are random:** tens to hundreds of µs, a different message each run. They're the OS and hardware, so **no maximum is claimed.**
- **A reproducible core exists.**
  - Fenced: 180 messages are slow in every run; 99.4% of them created a level, and 162 are adds.
  - Plain: 311 messages; 95.8% created a level, and 251 are adds.

**Test 2: what happened to the book's vector?** This was a separate scratch experiment, 1 run, fenced clock, tagging every add by what the vector did:

| add that… | count | p50 | p99 | p99.9 | p99.99 |
|---|---|---|---|---|---|
| creates no level | 737,541 | 84 | 336 | 609 | 2,564 |
| creates a level, no reallocation | 559,392 | 92 | 384 | 673 | 3,590 |
| **creates a level and the vector reallocates** | 6,764 | **304** | **1,667** | **17,441** | 32,512 |
| creates the first level on an empty side (allocation) | 8,810 | 208 | 801 | 4,616 | 24,577 |

**The reproducible tail is memory allocation.** When a book side's `std::vector` grows, it asks the allocator for a bigger block and copies the levels across. That happens on only ~1.2% of adds, but it is 3–25× slower than an insert that doesn't allocate.

**A tested fix that didn't help:** reserving 64 levels on first use.
- Reallocations fell to 60 in total.
- But the overall p99.99 didn't move, because the first allocation on each side still happens, and the rest is cache misses and OS noise.
- The real fix is **no allocation at all while processing messages** (fixed-size per-book arrays or a pre-allocated pool). Recorded as the next optimisation, not done.

## What I would and would not claim

- ✅ **Median ≈ 42–44 ns of work per message; p99 ≈ 240–310 ns; p99.9 ≈ 560–600 ns.** Consistent across runs and both clocks within the ranges shown, on this machine and this pre-market file.
- ✅ **p99.99 ≈ 1.4–2.7 µs.** Given as a range, because it depends on the clock and varies by run.
- ✅ **Messages that change a price level have a 3.3–3.4× heavier p99.99; within that, creating a level (A, U) drives it and erasing (D) barely matters.** The reproducible part is vector allocation.
- ❌ **No claimed maximum.** It's set by Windows and the laptop.
- ❌ **Not comparable with the throughput figures (67–69 ns/msg).** Those are pipelined and unfenced; these are one message at a time.
- ⚠️ **Pre-market data only** (27k live orders at peak). A full day has bigger books and more live orders, so expect a heavier tail.
